# 一键打包 LCode 安装包

> 目标：不用记 electron-builder 的参数，也不用记内核冻结/ESP-IDF 裁剪的顺序——
> **双击一个 bat 或跑一条命令**就出安装包。本文是这套流程的说明；
> 原理与体积细节见 `docs/打包发布指南.md`（§3 规划器、§11 两个版本）。

## ⚠️ 当前状态（2026-09-13 实测）

| 版本 | 状态 | 实测 |
|---|---|---|
| 不带 ESP-IDF | ✅ **可用** | 安装包 120.3 MB → 静默安装 368 MB/640 文件 → 启动后**随包内核就绪**（`useExe=true`）、图标随包生效、规划器就绪 |
| 带 ESP-IDF（B 方案） | ✅ **已实装并验证** | 载荷打成 `esp-idf-payload.zip`（**742 MB**）随安装包；应用**首次运行自动解压**到 `%APPDATA%\LCode\components\esp-idf`（2,405 MB / 57,580 文件，**94 秒**），随后用该组件真编译 blink 成功（`ok=True, 125s, blink.bin 191.5 KB`），编译器确认来自组件目录 |
| 知识库（组件） | ✅ 机制已验证 | `--no-kb` 冻结内核 + 外部载荷目录 → `kb_backend=private, kb_docs=634`；载荷约 1,383 MB → 归档约 432 MB（`tools/stage-kb-payload.py`） |

### 为什么是"组件 + 首次运行解压"（B 方案）

NSIS 的数据块上限是 **2 GiB**：把 ESP-IDF 目录（2.4 GB）直接装进安装包时，安装包能打出来、
但**安装时崩溃**（exit `0xC0000005`，一个文件都没进去）。所以：

```
安装包（NSIS）里只放一个 742 MB 的归档（未压缩数据 < 2 GiB ✓）
   └─ 首次运行：应用用 Windows 自带 tar.exe 解压到 %APPDATA%\LCode\components\<组件>
        └─ 注入环境：ESP-IDF → IDF_PATH / IDF_TOOLS_PATH / IDF_PYTHON_ENV_PATH
                     知识库 → LCODE_KB_PAYLOAD（内核把它插进 sys.path）
```

两条实现要点（都踩过坑）：

1. **冻结内核不能 `pip install`**：打包后的内核 Python 运行时在包里，所以知识库以"目录"形式提供，
   内核把载荷的 `site-packages/` 与根目录插进 `sys.path` 后 `import lcode_kb` 即可（实测 634 条向量可读）。
2. **解压后必须修 `pyvenv.cfg`**：ESP-IDF 组件的 `python_env/pyvenv.cfg` 里 `home` 指向打包时的
   **暂存路径**，换台机器就加载不到 Python DLL。应用解压后会把 `home` 重写到组件目录内的
   `python310`（`components.ts` 的 `postInstallFixup`）。实测：把暂存目录改名隐藏后，组件的
   `base_prefix` 仍指向组件自身，编译照常成功。

## 0. 两种版本（用户自选）
| 版本 | 产物名 | 内含 | 谁该下载 |
|---|---|---|---|
| **不带 ESP-IDF** | `LCode-<版本>-win-x64-setup.exe` | 壳 + Python 内核 | 本机**已有 ESP-IDF 环境**的用户（自己在设置页填路径即可） |
| **带 ESP-IDF** | `LCode-<版本>-win-x64-setup-full.exe` | 上者 + 裁剪后的 ESP-IDF 2.4 GB（含自带 Python 与工具链） | 什么都没装的用户，**装完即可编译固件** |

> 带 IDF 的版本体积约 1.0~1.3 GB（载荷压缩后）。载荷**不进 git、不进公开仓**，由脚本从你本机已安装的 ESP-IDF 现场裁剪生成。

## 1. 最快用法

```powershell
# 方式一：双击仓库根的「打包-LCode安装包.bat」，按菜单选 1/2/3
# 方式二：一条命令
powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1 -Variant full
```

`-Variant` 取 `base`（不带 IDF）/ `full`（带 IDF）/ `all`（两个都出）。

## 2. 脚本干了什么（六步，任一步失败即停）

```
1/6 检查前置：lcode\desktop 依赖、内核 venv、electron-builder
    ⚠ 随包规划器与 Electron 的兼容性门禁（见 §0.1）
2/6 冻结内核：lcode\kernel\scripts\build_kernel.py  →  lcode\desktop\resources\kernel\lcode-kernel(.exe)
3/6 裁剪 ESP-IDF（仅 full）：tools\stage-esp-idf.py  →  lcode\desktop\resources\esp-idf（2.4 GB）
4/6 桌面端构建：npm run typecheck → npx electron-vite build（产物进 out\）
5/6 出安装包：npx electron-builder --win [--config electron-builder.full.yml]
6/6 列出产物清单（名称 + 体积）与后续步骤提示
```

### 0.1 随包规划器要求 Electron ≥ 36.9（不满足会直接拒绝打包）

规划器闭包（`lcode\desktop\resources\planner`，由 `tools\build-planner-bundle.ps1` 生成）是用
**Electron 自带 Node**（`ELECTRON_RUN_AS_NODE=1`）跑的，而 DSH 需要 **Node ≥ 22.19**
（`node:zlib` 的 `createZstdDecompress`）→ 对应 **Electron ≥ 36.9**（推荐 38.x）。

老 Electron 上**不会崩**，而是规划器永远起不来、对话静默退化成精简模式（少 plan-mode / 推理等级 /
子代理）——**一个看起来正常的哑火包**。所以 `build-installer.ps1` 第一步就会拦住：

```
    [FAIL] bundled planner requires Electron >= 36.9 (bundled Node >= 22.19),
           but this tree has  v33.4.11 -> Node 20.18.3
           Fix:  cd lcode\desktop;  npm i -D electron@38.8.6   (close the running app first)
           Or override for an intentional slim build:  -AllowOldElectron
```

修法就是升级（`npm i -D electron@38.8.6`，**需先关掉正在运行的实例**——`node_modules\electron\dist`
里的文件被占用时会报 `EBUSY: ... icudtl.dat`）。真想只出精简版包才用 `-AllowOldElectron`。

## 3. 参数

| 参数 | 取值 | 默认 | 说明 |
|---|---|---|---|
| `-Variant` | `base` / `full` / `all` | `full` | 出哪种安装包 |
| `-KernelMode` | `auto` / `light` / `kb` | `auto` | `auto`：内核 venv 里装了私有知识库包 `lcode_kb` 就把它打进内核（**安装包会大 1 GB 以上**），否则出轻量内核；`light` 强制不含知识库（通用模式，检索返回空）；`kb` 强制包含 |
| `-EspIdfSrc` | 路径 | `D:\esp` | 用于裁剪的 ESP-IDF 安装根（Windows 官方安装器布局：含 `frameworks\` 与 `.espressif\`） |
| `-EspIdfTargets` | 逗号分隔 | `esp32s3` | 目标芯片。含 `esp32c3/c6/h2` 会带上 riscv32 工具链（**载荷 +2.4 GB**） |
| `-RebuildKernel` | 开关 | 关 | 强制重新冻结内核（改了内核代码后必须加） |
| `-RestageEspIdf` | 开关 | 关 | 强制重新裁剪 ESP-IDF 载荷（换了 IDF 版本后必须加） |
| `-SkipTypecheck` | 开关 | 关 | 跳过桌面端 typecheck（不建议） |

**复用规则**（省时间的关键）：脚本默认**复用**已存在的冻结内核与已生成的 IDF 载荷，只在缺失时才重建。
所以日常改 UI 只需几十秒；改了内核 Python 代码加 `-RebuildKernel`；换了 ESP-IDF 加 `-RestageEspIdf`。

## 6. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `electron-builder missing` | `cd lcode\desktop; npm install` |
| `kernel venv python not found` | 内核实现在 `lcode\kernel\.venv`（见上"一次性前置"） |
| `ESP-IDF source not found` | 传 `-EspIdfSrc <你的 IDF 安装根>`，或改用 `-Variant base` |
| 载荷只有 2 GB 缺工具链 | 你的 ESP-IDF 是用官方安装器装的吗？手动 clone 的请用 `stage-esp-idf.py --framework ... --tools ~/.espressif` |
| 安装包装完提示"未找到 idf.py" | 首次运行会自动写入随包路径；若你之前手动配过 IDF，脚本不会覆盖（设置页可改） |
| 安装包过大/超 2 GB | 别用 `-KernelMode kb`（torch 1.1 GB）+ `-EspIdfTargets` 带 riscv；或改"安装时下载"方案 |
| 任务栏图标还是旧的 | Windows 图标缓存：取消固定再固定一次 |
| 改了内核代码但行为没变 | 冻结内核是**旧的** → 加 `-RebuildKernel` |
| 换了 ESP-IDF 版本但没生效 | 载荷是**旧的** → 加 `-RestageEspIdf` |
| `EBUSY: resource busy or locked, copyfile ...resources\kernel\lcode-kernel.exe` | 两种成因：① 有残留的 `lcode-kernel.exe` 进程或杀毒在扫（脚本已加独占检查+等 5s×6）；② **`extends` 的子配置里重列了父配置的 `extraResources`** → 同一文件被两个 worker 并行拷贝。子配置只写自己的载荷，别重复列 kernel/planner |
| 冻结内核启动就 `ModuleNotFoundError: No module named 'config'`（或 api/agent/db/rag） | PyInstaller 的 `--collect-submodules <pkg>` 被**同名目录**带偏：从仓库根构建时 `tools` 解析到了仓库根的 `tools/`（发布脚本那层），内核自己的包全没进包。现已改为**强制 cwd=内核目录 + 显式 `--hidden-import` 列出每个模块**（见 `build_kernel.py` 的 `_own_modules()`），并加了构建后自动冒烟 |
| 冻结内核构建"成功"但其实是坏的 | `build_kernel.py` 内置冒烟：构建完自动启动一次并查 `/api/health`，不通过直接构建失败（可用 `--no-smoke` 跳过，不建议） |

## 8. 构建后自动发生的验证

`build_kernel.py` 每次构建完会**真的启动一次冻结内核**并请求 `/api/health`，成功才继续：

```
[冒烟] 启动冻结内核并检查 /api/health ...
[冒烟通过] {"status": "ok", "kb_backend": "stub", "kb_docs": 0, "llm_configured": false}
```

这条守则是被坑出来的：本机出现过"PyInstaller 构建成功、装进安装包、启动才报
`No module named 'config'`"——一路带到最后一步才发现。冻结产物的问题只有**运行**才暴露。

## 9. 组件载荷（ESP-IDF / 知识库）

体积大的部件都不进安装包，而是打成**单个归档**作为"组件包"，由应用在首次运行（或用户手动）
解压到用户目录：

| 组件 | 生成命令 | 载荷/归档 | 解压后给内核的变量 |
|---|---|---|---|
| ESP-IDF | `python tools\stage-esp-idf.py --src D:\esp` | 2,405 MB → **742 MB** | `IDF_PATH` / `IDF_TOOLS_PATH` / `IDF_PYTHON_ENV_PATH` |
| 知识库 | `python tools\stage-kb-payload.py --kb-src D:\1_ai_project\lcode-kb` | 1,383 MB → **~432 MB** | `LCODE_KB_PAYLOAD`（内核插进 `sys.path`） |

- 应用侧实现：`lcode/desktop/src/main/components.ts`（状态/解压/修 pyvenv/注入环境），
  首次运行自动安装见 `main/index.ts` 的 `applyComponentsOnStartup()`；
- 设置页新增「**扩展组件（可选，单独安装）**」卡片：显示已安装/未安装、版本、目录，
  支持「从文件安装…」（选 zip）与「打开目录」；
- 安装位置：`%APPDATA%\LCode\components\<组件名>`（**用户目录**，避开安装目录写权限问题）；
- 归档本身也可手动解压（就是普通 zip），便于排障。

#### 9.1 载荷"缺依赖"的两种隐蔽形态（都实测踩过，务必按此验收）

`tools/stage-kb-payload.py` 按**包名清单**从内核 venv 拷依赖，实测漏过两类东西——它们都不会
被"健康检查"发现，却会让用户机上的检索直接崩：

| 形态 | 例子 | 症状 | 现在怎么处理 |
|---|---|---|---|
| **单文件模块** | `typing_extensions.py`、`threadpoolctl.py` | 只查 `sp/<name>` 目录永远判"缺"；transformers 等在**检索时**才炸 | `_resolve_entry()` 认 `<name>.py` / `.pyi` |
| **卫星 DLL 目录** | `numpy.libs`（20 MB）、`scipy.libs`（19.2 MB） | `import numpy` 即 `DLL load failed while importing _multiarray_umath`；健康检查只数 npy 条数 → 报 `kb_docs=0` 也看不出原因 | 自动并上 `<name>.libs` / `<name>_libs` |

> 教训：**"条数对得上"不等于"能用"**。`store_count()` 只读 `vectors.npy`/`meta.json`（不加载
> torch），所以 `kb_docs=634` 完全可以伴随一个不能检索的载荷。验收必须真跑一次检索。

**KB 组件包验收（实测命令与结果，2026-09-13）**：

```powershell
# ① 冻结内核加载载荷（只需几秒；证明 sys.path 注入 + 向量库可读）
#    LCODE_KB_PAYLOAD=<载荷目录>；期望 health：kb_backend=private, kb_docs=634
# ② 载荷真检索（会加载 torch + sentence-transformers + embedding 模型）
#    精确做法：临时 venv + 只装 langchain_core 的来源（内核 venv）借 .pth，
#    PYTHONPATH=<载荷>\site-packages;<载荷>，再跑 lcode_kb.retrieve_docs(...)
#    期望：lcode_kb/numpy/torch 都来自载荷，hits=3 且来源是真实手册 PDF
```

实测结果：①`kb_backend=private kb_available=True kb_docs=634`；
②`lcode_kb`/`numpy 2.2.6`/`torch 2.6.0+cpu` 全部来自载荷，`docs=634`，
`retrieve_docs('MPU-6050 I2C register address')` → 3 条命中（`外设手册\MPU-6050.pdf`）。
归档体积 **283 MB**（载荷 1,382 MB / 19,858 文件）。

## 10. 发布到 GitHub Release（"可下载的安装包"）

### 10.1 三条路，只有第三条能给终端用户用

| 做法 | 结论 |
|---|---|
| 把 exe 提交进 git | ❌ **绝对不要**：GitHub 单文件硬上限 **100 MB**（我们最小安装包 120 MB），仓库也会被撑爆 |
| 传 Actions artifact | ❌ 终端用户拿不到：artifact 需登录下载、**90 天过期**。只适合内部流转 |
| **上传到 GitHub Releases** | ✅ 附件对所有人可下载、不过期；**单文件上限 2 GiB**（我们最大 742 MB ✓） |

### 10.2 谁打哪个包

| 产物 | 在哪打 | 怎么上传 |
|---|---|---|
| `base` 版（不带 IDF）Windows/macOS/Linux | **CI**（推 `v*` tag 自动触发） | workflow 最后一步用 `gh release create/upload` 自动挂到 Release |
| **`full` 版（带 ESP-IDF）** | **本地**（载荷来自你本机已装的 IDF：2.4 GB 源 / 742 MB 归档，CI 里下载代价太大） | `tools\publish-release.ps1` |
| **知识库组件包**（闭源，~432 MB） | **本地** | 同上，但必须显式加 `-IncludeKb`（默认拒收，防止手滑传到公开 Release） |

### 10.3 操作步骤

```powershell
# (1) 打 tag 并推送 -> CI 自动构建三平台 base 版并挂到 Release
git tag v0.1.0; git push origin v0.1.0

# (2) 本地出 full 版（复用现成载荷）
powershell -ExecutionPolicy Bypass -File tools\build-installer.ps1 -Variant full

# (3) 先干跑看要传什么（不联网、不上传）
powershell -ExecutionPolicy Bypass -File tools\publish-release.ps1 -Tag v0.1.0 -Repo <你>/<仓库> -DryRun

# (4) 真上传（用 gh 登录态，或先设 $env:GH_TOKEN = 'ghp_...'）
powershell -ExecutionPolicy Bypass -File tools\publish-release.ps1 -Tag v0.1.0 -Repo <你>/<仓库>

# (5) 需要把闭源知识库组件也挂上去（只给授权用户时建议用私有 Release/私有源）
powershell -ExecutionPolicy Bypass -File tools\publish-release.ps1 -Tag v0.1.0 -Repo <你>/<仓库> -IncludeKb
```

`publish-release.ps1` 的防呆（写进脚本，不靠记性）：
- 超过 **2 GiB** 的附件直接拒收；
- `.env` / `*.pem` / `*.key` 直接拒收；
- **`kb-payload*` 默认拒收**，必须显式 `-IncludeKb`；
- 上传前列出文件名与体积并要求确认（`-Force` 跳过确认，`-DryRun` 只打印不联网）；
- Release 已存在则复用并 `--clobber` 覆盖同名附件（可重复执行）。

### 10.4 建仓前的密钥清点（实测）

本机含那份 DeepSeek API Key 的文件**只有两处**：

```
D:\1_ai_project\mcu_ai_agent\lcode\kernel\.env                        <- .gitignore 已覆盖
D:\1_ai_project\_lcode-archive\embedded-agent-stage1-2026-09-12\.env  <- 已移出仓库
```

导出目录 `lcode-public-export` 里**没有** `.env`（导出脚本每次都会扫一遍）。
到控制台重置 Key 之后记得把新值写回 `lcode\kernel\.env`：开发模式下 `.env` 优先级
**高于**设置页（`load_dotenv(override=True)`），不写回去内核会 401。

## 11. macOS / Linux

这套脚本是 Windows 版（内核冻结件、工具链、安装包格式都是平台相关的）。mac/linux 需要在**对应系统**上：

```bash
# 内核冻结（PyInstaller 不能交叉编译）
python3 lcode/kernel/scripts/build_kernel.py --no-kb
# ESP-IDF 载荷（布局不同：手动 clone 的 IDF + ~/.espressif）
python3 tools/stage-esp-idf.py --framework ~/esp/esp-idf --tools ~/.espressif
# 安装包
cd lcode/desktop && npm ci && npx electron-vite build
npx electron-builder --linux                # AppImage + deb
npx electron-builder --mac --arm64          # 需在 macOS 上；带 IDF 版加 --config electron-builder.full.yml
```

CI 矩阵（`.github/workflows/build-installers.yml`）已按三平台分开；带 IDF 的版本建议在自建/私有 runner 上构建并缓存载荷（下载 2.4 GB 会很慢）。
