# LCode 三平台打包发布指南（Windows exe / macOS dmg / Linux AppImage+deb）

> 适用仓库：本仓（`lcode/desktop` = Electron 壳、`lcode/kernel` = Python 内核、`lcode/planner` = DSH 规划器、
> 私有仓 `lcode-kb` = 闭源知识库）。
> 本文所有体积/结论都是本机实测，命令可直接复制。

## 0. 结论速览

| 平台 | 产物 | 能在本机（Windows）出吗 | 额外条件 |
|---|---|---|---|
| **Windows** | `LCode-x.y.z-win-x64-setup.exe`（NSIS 安装包）、`…-portable.exe`（免安装） | ✅ 能，今天就能出 | 无（首次会联网下载 nsis 工具） |
| **macOS** | `LCode-x.y.z-mac-x64.dmg`、`…-arm64.dmg` | ❌ 不能 | **必须在 macOS 上构建**（Apple 不允许交叉出 dmg；内核二进制也得在 mac 上打）；要给别人用时还差签名+公证 |
| **Linux** | `LCode-x.y.z-linux-x64.AppImage`、`…amd64.deb` | ❌ 不能 | **必须在 Linux 上构建**（本机可用 WSL2 / Docker，或直接交给 CI） |

**所以正解是 CI 矩阵**：一个 GitHub Actions workflow，三个 runner 各自"打内核 → 打壳 → 出安装包"。
已写好：`.github/workflows/build-installers.yml`（Windows/macOS/Linux 三 job，产物上传为 artifact；
**推 `v*` tag 时最后一步自动 `gh release create/upload` 挂到 Release**——artifact 只是内部流转，
给用户下载的必须是 Release 附件，见 [`docs/一键打包.md`](一键打包.md) §10）。

### 0.1 已确认的产品约束（2026-09-12）

> **用户要求：用户安装完就是可用状态，而且必须是全功能。**

由此确定（尚未动代码，先记录）：

1. **规划器路线必须走 §3 的 B（自包含闭包随包）**——路线 A（不带规划器）达不到"全功能"，
   路线 C（首启下载）达不到"装完即用"。B 的唯一代价是体积与每平台各构建一次。
2. 路线 A 的**精简模式降级仍要做**：不是为了出厂形态，而是作为 **B 失效时的兜底**
   （规划器闭包缺失/启动失败/版本不匹配时，别让用户面对一个哑掉的对话窗口）。
3. **体积必须按 §4.1 的路线 ① 压**：不压的话安装包 1.5~2.0 GB；压到 600~800 MB 才与
   Cursor（净安装 ~800 MB）/ WorkBuddy（解包 623 MB）同量级。

## 1. 装机后有哪些东西必须随包（本项目的真正难点）

Electron 壳本身不难，难的是它外面还挂着两个**独立运行时**：

| 部件 | 现状 | 体积（实测） | 打包要点 |
|---|---|---|---|
| Electron 壳（`lcode/desktop`） | 已配好 electron-builder（本目录 `lcode/desktop/electron-builder.yml`） | ~120 MB/平台 | 只需 `out/**` + `package.json` |
| **Python 内核**（`lcode/kernel`） | 开发模式直接跑源码；生产模式找 `resources/kernel/lcode-kernel(.exe)` | 源码很小，但依赖：torch **1113.7 MB**、numpy 24 MB、sentence_transformers 4 MB、langgraph 2.2 MB… | **必须按平台打二进制**（PyInstaller）；见 §2、§4 |
| **DSH 规划器**（`lcode/planner`） | 开发模式 `node --import tsx/esm <DSH checkout>/apps/cli/src/bin.ts` | DSH monorepo `node_modules` **1352.5 MB / 56,716 文件**；本机 profile 的 `node_modules` 只有 **3 个文件**（全是符号链接，指回 monorepo） | 出厂机不可能有 DSH 源码仓 → 必须换随包路线；见 §3 |
| 知识库（私有仓 `lcode-kb`） | 私有包 + 向量库 `data/rag_store`（634 条 / 1.7 MB） | 向量可忽略；**torch 是大头** | 随安装包分发（"闭源而非保密"）或走 C 方案服务端 |
| ESP-IDF | **不随包**（3 GB 级外部工具链，且和芯片/版本强绑定） | — | 装完由用户在**设置页「ESP-IDF 编译环境」**填写（本次已补，见 §8）；内核 `/api/health` 会回报 `idf_py` 是否可用 |

## 2. 铁律一：内核不能交叉编译

PyInstaller/Nuitka 的原理是"把**当前操作系统**的 Python 运行时打进产物"，因此在 Windows 上打不出
macOS/Linux 的内核二进制。三个平台各打一次，没有捷径。

已把打包脚本重写成**跨平台 Python**（原 `build_kernel.ps1` 是 Nuitka PoC，且解释器路径写的是
`..\..\embedded_agent_stage1\.venv\...`——那个目录已迁出仓库，脚本早就失效了）：

```powershell
# Windows 本机（产物直接落到 lcode\desktop\resources\kernel\）
cd lcode\kernel
.\.venv\Scripts\python.exe scripts\build_kernel.py            # 带私有知识库（正式版）
.\.venv\Scripts\python.exe scripts\build_kernel.py --no-kb    # 不带（公开仓/CI 版，体积小很多）
```

```bash
# macOS / Linux（同名脚本，同一套逻辑）
python3 lcode/kernel/scripts/build_kernel.py --no-kb
```

产物布局刻意与 `KernelManager` 的查找路径对齐（`resources/kernel/lcode-kernel(.exe)` + 同级 `_internal/`），
所以打完不需要改任何代码。

### 2.1 冻结内核实测踩到的三个坑（都已在脚本/内核里修好）

| 坑 | 现象 | 修法 |
|---|---|---|
| uvicorn 用**字符串**导入应用 | 冻结后启动即 `ModuleNotFoundError: No module named 'api'`（`uvicorn.run("api.main:app")` 是字符串，PyInstaller 静态分析看不见） | 脚本自动 `--collect-submodules` + `--hidden-import` 内核自己的 6 个包（`api/agent/tools/db/config/rag`） |
| 数据目录落在安装目录内 | 冻结后 `BASE_DIR` = `_MEIPASS`（`_internal/`），`tasks.db`/`outputs` 全在安装目录里 → Program Files 下**不可写**、升级还被清掉 | 内核新增 `--data-dir`；桌面端打包模式强制传 `%APPDATA%\LCode\kernel-data`（开发模式不传，保持 `lcode/kernel/data` 不动；旧版 `%APPDATA%\L-CODE` 启动时自动迁移到 `LCode`，见 `migrateLegacyUserData()`） |
| `--no-kb` 仍会打进 torch | `rag/backend.py` 里 `import lcode_kb` 是静态导入（包在 try 里），静态分析照样跟进 → 精简版内核被塞进 1.1 GB torch | 脚本在 `--no-kb` 时显式 `--exclude-module lcode_kb/torch/sentence_transformers/...` |

**实测结果**（本机 Windows）：

```
python scripts\build_kernel.py --no-kb
  → dist\lcode-kernel\lcode-kernel.exe，整包 94.8 MB
  → 已拷到 lcode\desktop\resources\kernel\
运行冻结产物：lcode-kernel.exe --port 18241 --token … --data-dir <可写目录>
  → GET /api/health = {"status":"ok","kernel_mode":true,"kb_backend":"stub","kb_docs":0,…}
  → 指定数据目录里生成了 tasks.db  ✅（可写性验证通过）
electron-builder --win --dir
  → dist\win-unpacked\LCode.exe ✅（配置可解析、extraResources 正常、未签名按预期跳过）
```

## 3. 铁律二：规划器怎么随包（三条路线）

开发模式那条命令要求用户机器上有：系统 Node + 完整 DSH 源码仓 + 1.35 GB `node_modules` + 手工建好的
`~/.dsh/profiles/lcode-planner`。**出厂机不可能有**，所以必须选一条：

| 路线 | 做法 | 代价 | 结论 |
|---|---|---|---|
| **A. 不带（当前默认）** | 安装包只带壳+内核。桌面端在规划器不可用时走**精简模式**：内核自带对话 Agent（`POST /api/chat` → `agent/chat_agent.py`）+ 固件流水线（选型→RAG→生成→编译→修复）。DSH 的 plan-mode / 子 agent / 多工具暂不可用 | 少一部分 Agent 能力；需补一段"规划器不可用时的降级路由 + UI 提示" | **先走这条**：三平台今天就能出包，体积可控 |
| **B. 自包含闭包随包** | 构建期在 DSH 源码仓里构建（`pnpm build:lib` → `packages/*/dist`），把「DSH 运行产物 + 运行期 node_modules + `@lcode/planner` 预编译成 JS + 预置 profile」放进 `lcode/desktop/resources/planner/`；运行时用 **Electron 自带 Node**（`ELECTRON_RUN_AS_NODE=1 process.execPath`）启动，用户无需装 Node | 每平台各构建一次（`node-pty`/`koffi` 是原生模块，不能跨平台复用）；安装包 +约 0.5~1.5 GB；DSH 版本要锁版回归 | 功能完整的正解，作为第二步 || **C. 首次运行下载运行时包** | 安装包很小，首启从你自己的服务器/Release 下载对应平台的 planner runtime pack | 必须联网；要自己托管 ~0.5 GB/平台；断网不可用 | 想压安装包体积时考虑 |

**实测证据（为什么不能"直接用 npm 上发布的 DSH 包装个闭包"）**：

```
pnpm add @deepseek-ai/dsh@latest（hoisted + 自动补 peer）
  → 失败：@deepseek-ai/dsh-type-meta is not in the npm registry
npm install @deepseek-ai/dsh@latest … 
  → 失败：peer @deepseek-ai/dsh-brand@"^0.0.1-rc.1" from @deepseek-ai/dsh-session@0.0.1-rc.1 冲突
参考：pnpm 装 4 个 DSH 包（不开自动 peer）= 24,872 项 / 215 MB，且 24,577 项是符号链接
      → 不是可分发的闭包；CLI 缺 peer 时立刻报 Cannot find package '@deepseek-ai/cordis-plugin-group'
```

即：`apps/cli` 的包名就是 `@deepseek-ai/dsh`（已发布 `0.1.5-rc.2`），但**它依赖的部分内部包没发布**，
所以闭包只能从源码仓构建（路线 B），不能靠 npm 拼。

路线 B 需要改的代码（目前 `planner-manager.ts` 只有开发分支）：

1. `dshRepoDir()`：`app.isPackaged` 时返回 `path.join(process.resourcesPath, 'planner')`；
2. 启动：`spawn(process.execPath, [runner, '--profile', 'lcode-planner'], { env: { ...env, ELECTRON_RUN_AS_NODE: '1' } })`；
3. `DSH_HOME` 指向可写位置（`app.getPath('userData')`，不能写安装目录）；
4. 规划器不可用时降级到内核 `/api/chat`。

### 3.1 路线 A 的"降级路由 + UI 提示"**已落地并实测**（2026-09-13）

原先"精简模式"只是文档里的打算，代码里没有：规划器不可用时 `chat:send` 直接抛
`E_PLANNER_NOT_READY`，用户面对的是一个"点发送没反应"的窗口。现在补齐了：

| 层 | 实现 | 位置 |
|---|---|---|
| 判定 | `planner.available`（运行时入口是否存在）+ `status === 'crashed'` → 精简；`starting` 先等 20 s | `lcode/desktop/src/main/planner-manager.ts`、`main/index.ts` 的 `chatSlimMode()` |
| 路由 | 精简时 `chat:send` → 内核 `POST /api/chat`（`sendViaKernel()`），事件仍轮询 `/api/events` | `main/index.ts` |
| 同能力接口 | 停止 → `/api/chat_cancel`；分支 → `/api/chat_fork`；权限 → `/api/chat_access` | `ipc-client.ts` |
| 不支持项 | plan-mode / 推理等级 / 待发送队列 / planner 人机交互 / 烧录二次确认 → 返回 `supported:false`（**不报错**，界面不弹错、不显示假 pill） | 同上 |
| 界面 | 聊天区顶部琥珀提示条「精简模式」；plan pill、+ 菜单、推理等级 pill 在精简模式下不渲染 | `lcode/desktop/src/renderer/src/components/ChatPane.tsx`、`i18n.ts` |
| 可观测 | `chat:mode` IPC 回 `{mode, reason, planner_status, planner_available, planner_error}` | 同上 |

**实测证据（真实 LLM 调用，隔离实例）**：起一个临时内核（临时端口/数据目录）→ `POST /api/chat`
（即精简模式实际走的那条路）→ 轮询 `/api/events` 与会话详情：

```
health: {"status":"ok","llm_configured":true,"kb_backend":"private","kb_docs":634,...}
POST /api/chat -> {"session_id":"16cbd271baf64f45","status":"running"}
事件字段: ['event_type','level','message','node','payload','seq','task_id','ts']
助手回复: '收到'   会话状态: idle   消息数: 2     → PASS
```

结论：**路线 A 今天就能出可用包**（对话/改码/编译主线通），代价是 plan-mode、推理等级、
子代理、待发送队列不可用——这些正是路线 B 要买回来的东西。

**打包版实测（2026-09-13，`electron-builder --win --dir` + 独立 userData 启动）**：

```
[kernel-manager] spawn: "...\resources\kernel\lcode-kernel.exe" --port 6463 --token … --data-dir <userData>\kernel-data
[kernel-manager] 内核已启动 pid= 38736
[planner-manager] 规划器不可用：未找到 DSH checkout（…\dist\deepseek\deepseek-harness-master\apps\cli\src\bin.ts）
                  → 对话将走精简模式（内核 /api/chat）
```

即**安装版确实会落到精简模式**（内核照常起、`--data-dir` 指向用户目录、窗口可用），
不会出现"点发送没反应"。剩下只差用户在界面上点一次发送的目视确认。

### 3.2 路线 B 的实测调研结论（2026-09-13，原型已验证）

原型在 `D:\1_ai_project\_planner_bundle_test`（**未改动本仓任何文件**），完整报告见该目录
`REPORT.md`。核心数字：

| 项 | 实测 |
|---|---|
| 裁剪后闭包 | **27.99 MB / 3914 文件 / 90 包** |
| ├ DSH 产物 `apps/cli` | 0.17 MB / 40 文件 |
| ├ DSH workspace 包（219 个 `lib/` 已就绪） | 17.49 MB / 2554 文件 |
| ├ 第三方依赖 | 10.24 MB / 1313 文件 |
| └ `@lcode/planner` 预编译单文件 | 0.08 MB（75,924 字节） |
| 未裁剪基线 | 176 MB（DSH heal 口径）/ 272 MB（完整声明闭包） |
| Electron-as-node 启动 → `/api/planner/health` 可达 | **1.52 s**；48 个插件全部挂载；5 个 GET 端点 200、错 token 401 |

**⚠️ 硬前置：必须升 Electron。** 当前 Electron **33.4.11** 自带 **Node 20.18.3**，而 DSH 声明
`engines: ^22.19.0 || >=24`（用到了 Node 22.15 才有的 `zlib.createZstdDecompress`）。实测报错：

```
SyntaxError: The requested module 'node:zlib' does not provide an export named 'createZstdDecompress'
```

原型是在 **Electron 38.8.6（Node 22.22.0）** 上跑通的，所以路线 B 的落地顺序是：
**先升 Electron（≥36.9.0，首个自带 Node 22.19 的稳定版）→ 再打包 planner 闭包**。
升级牵动 electron-vite 3 / electron-builder 25 与原生模块重编译，属**未验证工作量**。

**三个坑（都实测踩过）**：

1. **不要重建、不要重装**：DSH 219 个包的 `lib/` 产物已齐全（workspace 是**嵌套**的
   `packages/<group>/<name>`，直接查 `packages/<name>/lib` 会误判成 0 个），`node_modules`
   1.32 GB 也不必动。pnpm 11.7.0 / corepack 0.34.6 本机可用。
2. **静态裁剪不安全**：`koffi` 的原生二进制在 `optionalDependencies`
   （`@koromix/koffi-win32-x64`）里，静态 import 扫描永远看不到 → 裁剪后必须配
   **"真启动一次 + 打 health"** 的门禁（与我们冻结内核冒烟同一个思路）。
3. **`@lcode/planner` 不按 `$DSH_HOME/profiles/node_modules` farm 解析**：Loader 以 profile
   目录为基准 import，所以 `DSH_HOME` 放在闭包内只是巧合成立；用真实 `~/.dsh` 时必须
   seed profile 目录并在 profile 内建 `@lcode/planner` junction（实测无需管理员权限）。

**桌面端接线已就绪**（本轮已实现，等闭包产出即可用）：`planner-manager.ts` 的
`resolveRuntime()` 优先取随包入口（`LCORE_PLANNER_DIR` 或 `resources/planner/`，
候选 `run-planner.mjs` / `runner.mjs` / `index.mjs` / `cli/bin.mjs`），随包模式用
`process.execPath` + `ELECTRON_RUN_AS_NODE=1` 启动，并把 `DSH_HOME` 指到
`userData/dsh-home`（安装目录不可写）；两者都不存在时才回落精简模式。

**尚未验证**：Electron 升级本身；规划器**对话主链路**（原型里内核与 LLM 都指向不可达地址，
只证明了 HTTP 服务能起来）；`workflow-worker-thread` 的 worker 线程在 Electron-as-node 下
能否启动（风险最高的一项）。

### 3.3 路线 B **已落地并实测**（2026-09-13）

一键脚本：`tools/build-planner-bundle.ps1`（四步 + 启动门禁，纯 ASCII）：

```
[1/4] 预编译 planner（esbuild 单文件 ESM，裸标识符保持 external）
[2/4] 静态闭包分析 → 90 包 / 0 个未解析标识符 / 27.44 MB
[3/4] 落到 lcode/desktop/resources/planner → 27.99 MB / 3915 文件
[4/4] 启动门禁：拷到临时目录 → Electron-as-Node 启动 → 轮询 /api/planner/health
      → {"status":"ok","name":"lcode-planner","model":"deepseek-v4-flash",...}
```

**打包版端到端实测**（`electron-builder --win --dir` + Electron 38 + 独立 userData 启动）：

```
[planner-manager] 随包运行时已就位: <userData>\planner-runtime (8 s, 版本 0.1.0)
[planner-manager] 忽略继承的 DSH_HOME = C:\Users\F\.dsh（随包运行时用自己的 home： …\planner-runtime\home）
[planner-manager] start: 运行时 = bundled | 入口 = …\planner-runtime\apps\cli\lib\bin.js
                  | launcher = electron-node | cwd = …\planner-runtime | DSH_HOME = …\planner-runtime\home
[planner] HTTP 服务已启动：http://127.0.0.1:13726
[planner-manager] 健康检查通过，规划器就绪 pid= 35132
[planner-manager] 规划器生效配置: 模型 = deepseek-v4-flash
```

即**安装版开箱即有规划器**（不再要求用户装 Node / DSH 源码 / 手工建 profile）。

实现要点（都踩过坑才写下的）：

1. **随包闭包整份拷到 `%APPDATA%\LCode\planner-runtime`**（首次 6~15 s / 28 MB，按 manifest
   版本+构建时间戳幂等跳过）。为什么要拷：安装目录可能只读，且 DSH 要往 DSH_HOME 写
   sessions/settings/凭据；更关键的是**必须保留 `node_modules/` 与 `home/` 的相对布局**，
   profile 里的 `import('@lcode/planner')` 靠父目录上溯命中（REPORT 坑 3）。
2. **随包模式必须无视继承的 `DSH_HOME`**：装了 DSH GUI 的机器环境里常有 `DSH_HOME=~/.dsh`，
   一旦沿用，profile 会解析到**开发源码** `lcode/planner/src/*.ts`，Node 22 strip-only 模式直接报
   `TypeScript parameter property is not supported in strip-only mode`。现在只在随包模式用闭包
   自带的 `home/`（测试要用别的 home 走 `LCORE_PLANNER_DSH_HOME`）。
3. **Node 版本门禁**：`process.versions.node < 22.19` 时不启用随包运行时（否则必炸 zstd import），
   开发机上有 DSH checkout 就继续用它 —— 避免"闭包一放进 resources 就把开发环境弄坏"。
4. **闭包分析要可自愈、缺包要硬失败**：实测闭包不幂等（pnpm farm 被重写后，90 个包里 27 个
   原路径失效；planner 自己 import 的 `@deepseek-ai/dsh-sandbox-policy` 不在 CLI 依赖闭包里）。
   现在解析失败会按包名回 DSH `.pnpm` store / workspace 兜底（**按 package.json 的 name 比对，
   不能猜目录名**：包名带 `dsh-` 前缀、目录名不带），仍缺则 `build-bundle.mjs` 直接 exit 1，
   绝不产出残缺闭包。另外闭包里原生二进制藏在 `optionalDependencies`（`koffi`），静态扫描看不见
   —— 所以**启动门禁不是装饰**。


## 4. 体积预算（决定安装包大小）

| 组成 | 体积 | 备注 |
|---|---|---|
| Electron 运行时 | ~120 MB/平台 | 固定 |
| 内核 PyInstaller | 通用模式（`--no-kb`）约 80~150 MB | 只有 fastapi/langgraph/langchain |
| 内核 + 私有知识库 | **约 1.2~1.8 GB** | torch 占 1.11 GB ❗ |
| 规划器闭包（路线 B） | 约 0.5~1.5 GB | DSH 运行期依赖 |
| 知识库向量 | 1.7 MB | 可忽略 |

**建议**：把知识库的 embedding 从 `torch + sentence-transformers` 换成
`onnxruntime + bge-small-zh-v1.5 (int8)`（约 30~50 MB），安装包能从 ~1.5 GB 压到 ~300 MB。
**这一条只动私有包**——方案 A 的接缝已经把知识库隔离在 `lcode_kb` 里，公开仓一行都不用改。

### 4.1 对标实测：Cursor / WorkBuddy 是怎么打包的，为什么"那么小"

本机实测（2026-09-12，`Get-ChildItem -Recurse` 统计）：

| 对象 | 数值 |
|---|---|
| **Cursor**（安装目录 `%LOCALAPPDATA%\Programs\cursor`） | 合计 **1,688.8 MB**；其中 `_` 目录 **873.2 MB**（**上一版本备份**，用于自动更新回滚，不算首次安装）、`resources\app` **436.0 MB**（**未打包的目录**，VS Code 风格）、`Cursor.exe` 201.3 MB |
| Cursor `resources\app` 组成 | `node_modules` 128 MB / `extensions` 102.7 MB / `resources` 94.2 MB / `out` 73.8 MB / `bin` 37.1 MB |
| Cursor 里的 **Python / torch / onnx / .pt / .safetensors** | **一个都没有** |
| Cursor 安装器 | Inno Setup（`unins000.exe`） |
| **WorkBuddy**（解包产物） | 合计 **622.8 MB**：`node_modules` **375.1 MB**、`renderer` 139.7 MB、`cli` 45.4 MB、`resources` 41.3 MB、`main` 21.0 MB；同样**无 Python、无本地模型** |
| 我们内核 venv 的重依赖 | torch **1,113.7 MB**、scipy 102.9、transformers 50.1、onnxruntime 37.3（已装）、sympy 33.0、sklearn 28.7、numpy 24.0、tokenizers 7.5、networkx 6.1、sentence_transformers 4.0 |
| 我们的 embedding 权重 | `BAAI/bge-small-zh-v1.5` **91.9 MB**（HF 缓存实测） |

**结论（三条，别被"小"误导）**：

1. **它们不小**：Cursor 净安装约 800 MB（去掉更新备份），WorkBuddy 解包 623 MB。它们的
   JS 运行时依赖同样是几百 MB（WorkBuddy `node_modules` 375 MB、Cursor `app` 436 MB）——
   这一块我们和它们同量级，不是差距所在。
2. **差距只在"模型在谁那边"**：它们客户端里**没有任何本地 ML 栈**，嵌入与推理全在服务端。
   我们为了"本地检索手册"在客户端跑了 torch（1.11 GB）+ transformers/scipy/sklearn 连带（约 320 MB）。
   **这 1.4 GB 就是全部差距来源。**
3. **安装器 ≠ 安装后体积**：压缩 + 增量更新 + 运行时按需下载，能让下载体积远小于安装体积。
   Cursor 那个 873 MB 的 `_` 目录正说明它是"整包替换式更新"。

**保持"装完即全功能"又能瘦下来的三条路**（可叠加）：

| 路线 | 做法 | 预计影响 |
|---|---|---|
| **① 本地知识库不跑 torch**（性价比最高） | 私有包把 embedding 换成 `onnxruntime`（本机已装 37.3 MB）+ bge-small 的 ONNX int8 权重（约 30~90 MB）；顺带卸掉 transformers(50)/scipy(103)/sklearn(29)/sympy(33) | 内核 ~1.5 GB → **~250~350 MB**；**只动私有包**，公开仓零改动 |
| **② 知识库检索服务端化**（= Cursor 的做法） | 检索走你的网关（C 方案），客户端连 onnxruntime 与 91.9 MB 权重都不带 | 再省约 150 MB，但**必须联网**且你要托管语料/向量 |
| **③ 规划器闭包瘦身** | 从 DSH 源码仓构建 `packages/*/dist` + 只装运行期依赖（**不要**带 monorepo 那 1.35 GB devDependencies）+ 用 Electron 自带 Node（`ELECTRON_RUN_AS_NODE`）免装 Node | 规划器运行时目标 **~200~400 MB** |

**目标体积对照**：现状方案（本地 torch + 规划器闭包）安装包约 **1.5~2.0 GB**；
加上路线 ① 后约 **600~800 MB**（≈ Cursor 净安装量级）；再加 ② 约 **500~700 MB**。
一句话：**"装完全功能 + 体积不夸张"能做到，关键是不在客户端跑 torch。**

### 11.1 为什么不能直接把 `D:\esp` 塞进安装包

本机实测 `D:\esp` = **9.35 GB**，其中大部分与运行无关：

| 部分 | 体积 | 处置 |
|---|---|---|
| `.espressif\dist`（下载缓存） | 1,227 MB | ❌ 丢（只有 IDF 安装器/离线重装需要） |
| `.espressif\releases`（下载缓存） | 1,906 MB | ❌ 丢 |
| `frameworks\esp-idf-v5.5.5\.git` | 1,805 MB | ❌ 丢（实测只剩 `WARNING: Git version unavailable, reading from source`，无害） |
| `.espressif\tools\riscv32-esp-elf` | 2,387 MB | ❌ 丢（只有 esp32c3/c6/h2 需要；esp32s3 用 xtensa） |
| 框架源码（components/docs/examples/tools） | 458 MB | ✅ 保留（`--no-docs` 再省 70 MB） |
| `.espressif\tools\xtensa-esp-elf` | 1,356 MB | ✅ 保留（esp32s3 编译器） |
| 其它工具（gdb 125 / cmake 112 / ulp 39 / idf-python 39 / openocd 7 / …） | ~330 MB | ✅ 保留（`--no-gdb --no-optional` 省 140 MB） |
| `.espressif\python_env` | 68 MB | ✅ 保留 |
| **基础 Python 3.10**（`pyvenv.cfg` 的 `home` 指向它） | 180 MB | ✅ 保留（否则用户机没装 Python 就跑不起来） |

**裁剪后载荷 ≈ 2.4 GB**（`--no-gdb --no-optional --no-docs` 可到 2.2 GB）。⚠️ 这份载荷**不能**直接塞进
NSIS 安装包（数据块 >2 GiB 会在**安装时崩溃**，见 §11.5），实际做法是打成 `esp-idf-payload.zip`
（**742 MB**）随包、首次运行解压到用户目录。

```powershell
python tools/stage-esp-idf.py --src D:\esp --dry-run      # 只看计划与体积（秒级）
python tools/stage-esp-idf.py --src D:\esp                # 生成载荷（2.4 GB，实测约 8 分钟）
# macOS / Linux（布局不同：手动 clone 的 IDF + ~/.espressif）
python tools/stage-esp-idf.py --framework ~/esp/esp-idf --tools ~/.espressif
```

### 11.2 搬迁必须修的三处（否则"装完编译不了"）

| 问题 | 现象 | 处理 |
|---|---|---|
| `python_env\pyvenv.cfg` 的 `home` 指向**本机系统 Python** | 用户机没装 Python 3.10 → venv 起不来 | 脚本连**基础 Python 一起打包**（`payload/python310`）并改写 `home`；实测 `sys.base_prefix` = 随包 Python ✓ |
| `.espressif\idf-env.json` 记着**旧绝对路径** | IDF 视角路径错乱 | 脚本删除该文件（`idf.py` 不需要） |
| `.espressif` **根目录散文件**必须带 | 缺 `espidf.constraints.v5.5.txt` 时 `idf.py` 直接报 *"Perhaps you've forgotten to run the install scripts"* | 保留 `espidf.constraints*` / `idf_cmd_init.*` / `idf_tools_fallback.py` / `tools_fallback.json`（**实测踩过**） |

### 11.3 内核侧配套改动（关键）

`lcode/kernel/tools/compile_tool.py` 新增**自己拼编译环境**（`_tool_bin_dirs()` + `_build_env()`），
不再依赖 `export.bat`，原因三条：

1. `export.bat` 要求 PATH 里已有 **`python.exe` 与 `git.exe`**——随包用户机上不一定有；
2. `idf_tools.py export`（`export.bat` 内部就调它）会校验 tools.json 中所有 **`install: always`** 的工具。
   实测 `riscv32-esp-elf` 正是 `always`，而它为省 2.4 GB 被砍掉 → `ERROR: tool riscv32-esp-elf has no
   installed versions` 直接失败（`--targets` 它也不认）。**"砍 riscv"与"用官方 export"二者不可兼得**；
3. 各工具目录布局不统一（`xtensa-esp-elf/<ver>/xtensa-esp-elf/bin`、`cmake/<ver>/bin`、
   `ninja/<ver>/` 直接放 exe）→ 按"哪一层有可执行文件"扫描，而非写死结构。

新的调用优先级：**自建环境直接跑 `python idf.py`** →（拼不出时）`export.bat` 包装 →（再不行）PATH 里的 `idf.py`。
并补齐 `ESP_ROM_ELF_DIR` / `OPENOCD_SCRIPTS`。

```powershell
# 1) 不带 ESP-IDF（默认配置）
cd lcode\desktop
npx electron-builder --win                                      # → LCode-x.y.z-win-x64-setup.exe

# 2) 带 ESP-IDF（先生成载荷）
python tools\stage-esp-idf.py --src D:\esp
cd lcode\desktop
npx electron-builder --win --config electron-builder.full.yml   # → …-setup-full.exe
```

- `electron-builder.full.yml` 用 `extends` 复用基础配置，**只列自己那份载荷**：electron-builder 的
  数组字段是**拼接（父 + 子）而不是覆盖**——早期版本把父配置的 `extraResources` 又重列了一遍，
  结果两个 builder worker 并行拷同一个 `lcode-kernel.exe`，构建报
  `EBUSY: resource busy or locked, copyfile ...`（实测踩过两次）；
- 产物名带 `-full` 后缀，用户一眼区分；
- ⚠️ **NSIS 单文件安装包塞不下 2.4 GB**（实测：载荷 2,771 MB → 出包 640.9 MB，**安装时崩溃**
  `exit -1073741819` / `0xC0000005`，NSIS 数据块上限 2 GiB）。因此带 IDF 的版本改用 **B 方案**：
  载荷打成 `esp-idf-payload.zip`（2,405 MB → **742 MB**）随包，首次运行解压到
  `%APPDATA%\LCode\components\esp-idf`（实测自动安装 94 秒），再由
  `components.ts` 的 `componentEnv()` 注入 `IDF_PATH` / `IDF_TOOLS_PATH` / `IDF_PYTHON_ENV_PATH`；
  解压后必须把 `python_env\pyvenv.cfg` 的 `home` 改写为**组件目录下**的 `python310`
  （否则会指向打包机的 staging 路径，实测踩过）。知识库组件同理（`LCODE_KB_PAYLOAD`）。
- **载荷不进 git / 不进公开仓**：`.gitignore`、`tools/make-public-export.ps1`、
  `tools/publish-release.ps1` 三处都已排除（发布脚本对 `kb-payload*` 默认**拒收**，须显式 `-IncludeKb`）；
- **许可证**：ESP-IDF 本体 Apache-2.0，工具链各自许可见其目录内 LICENSE（GPL/LGPL 系）。
  分发带 IDF 的版本时随包保留这些许可证，并在关于页/安装界面给出出处声明；
- 若将来还要把 KB 的 torch（1.1 GB）也塞进同一个归档，压缩后会逼近 2 GiB 附件上限，需要拆分载荷。
