## 2. 中层：编排层（V3.1 改道 · DSH workflow agent 脚本编排；确定性 schema 执行器降为后置可选载体）

> **V3.1 改道**：中层主线改为 **DSH workflow agent 脚本编排**（`dsh-workflow` + worker-thread +
> `dsh-tool-workflow`，fan-out 子 agent，见第 8 章 Phase 4 / 附录 D）。本章 2.1–2.3 原文属
> V2.4–V2.8"确定性 schema 执行器 + run_workflow"历史设计：仅当"一键生成固件"等固定流程需要
> **确定性**表达时作为可选载体保留（FlowSpec 后置可选），不再承担 Phase 4 主线角色。
> 其余章节凡言"流程执行器（可选 · 后置）"处，按此改道理解：编排=DSH workflow（Phase 4），
> 确定性 schema 执行器=后置可选固件流程载体。

### 2.1 定位与边界（历史主线文案 · 确定性载体保留）

- **只做确定性**：固定多步流程（步骤 + 条件分支 + 计数重试 + 检查点）。
- **禁止开放规划**：固定流程只执行既定步骤，"走哪条路、用什么工具"是规划层的事。
- **按需启用 · 当前主路径不经过**：通用对话/编辑场景直接"规划循环 → 底座工具"，不引入编排/执行器；仅在需要固定流程（如后续"一键生成固件"）时启用。
- **不用 LangGraph 核心**：中层不依赖 LangGraph。行业参照（Cursor、Qoder、Claude Code 等产品）均自研 agent loop，其"确定性步骤"用工具/技能表达，不用图引擎。当前实现 = 轻量 **schema 化步骤执行器**（`{steps: [{id, tool, input}], conditions, checkpoint}`）；最简形式甚至不引入执行器——规划层 LLM 按序调工具即可。
- 对规划层只暴露一个工具：`run_workflow`（**后置实现**；V3.1 起主路径改为 DSH `workflow` 工具，见 Phase 4）。

### 2.2 流程注册表（可选 · 后置实现）

需要固定流程时，以 schema 声明式注册（**不用 LangGraph**）：

```
FlowSpec {
  flow_id: "firmware_build" | "ts_refactor" ...
  description: string
  input_schema: JSON Schema      // 入参校验
  output_schema: JSON Schema     // 结构化结果
  steps: [{id, tool, input}]     // 步骤列表（可含条件分支）
  checkpoint_policy: "step" | "none"
}
```

### 2.3 run_workflow 契约（后置实现）

```
run_workflow(flow_id, input, resume?)
  → {
      result,                 // 按 output_schema 的结构化结果
      artifacts,              // 产物清单（工程文件、日志、bin…）
      checkpoint_id,          // 本次执行 checkpoint（供 resume）
      usage,                  // LLM token 用量汇总
      events,                 // 本次流程事件
    }
resume(checkpoint_id)            // 从断点继续（步骤级续跑，后置）
cancel(task_id)                  // 步骤执行前检查取消标志
```

**V1 不实现**：当前对话/编辑主路径由规划层直接调工具完成，无需 run_workflow。

### 2.4 checkpoint 与断点续跑

- **V1 以会话级为主**：规划层事件溯源（会话日志持久化）+ goal 续跑已提供断点恢复能力，`/api/resume_task` 沿用现有实现。
- 流程级 checkpoint（步骤级断点）**后置**：待流程执行器落地时再实现，不依赖 LangGraph checkpoint。

### 2.5 流程事件（后置）

流程执行器落地后，`flow/start`、`flow/step`、`flow/end` 自动落 events 表，与规划层 turn/step 事件统一（5.2 事件字典）。V1 对话主路径仅产生规划层事件。

### 2.6 固件生成流程（原 LangGraph 流水线 → 对话式）

**新架构不再依赖 LangGraph 子图**。V1 固件生成走**对话式**：规划层 LLM 在会话中按序调用工具（`rag_search` 查芯片手册 → `code_generate` 生成工程 → `build` 编译校验），校验诊断返回给规划层/用户决策，**会话确认结束后显式烧录**。

**自动修复回环（compile → error_fix → 再编译）暂缓**：V1 由 LLM 在对话中根据诊断进行决策式迭代修改，不做自动化闭环（见 3.3）。

原有 LangGraph 流水线（chip_select → rag_search → code_generate → compile_build → error_fix）保留为**历史实现参考**（实现细节见 `docs/嵌入式垂直 Agent 阶段 1 MVP 完整开发文档.txt`）；后续如需"一键生成固件"的固定流程，用轻量流程执行器（2.2）重新表达，不引入图引擎。

## 10. 核心参考开源项目清单（精准借鉴点）

1. **DeepSeek Harness（DSH）**：上层规划层（agent-loop 的 turn/step 循环与瀑布钩子、goal 与 goal-round-driver 续跑、tools 工具系统、session 事件溯源、plan-mode）——headless 组装复用的直接来源
2. **cordis**：插件框架（`apply(ctx)`、`ctx.on`、waterfall/serial 调度、effect 生命周期）——规划器插件系统基座
3. **LangGraph**：曾为中层编排候选（StateGraph、条件路由、checkpoint-sqlite 断点续跑）；V2.4 起中层不再依赖，保留为流程执行器的候选实现参考
4. **rust-analyzer**：增量缓存、快照架构、内核与协议解耦、重构模块设计（后置可选能力 3.6 的借鉴点）
5. **salsa**：增量依赖计算、缓存失效机制（后置可选；V1 不建全工程索引）
6. **ts-morph**：TS 语义重构工具（后置可选，按 profile 提供，跨文件重命名/提取）
7. **tree-sitter**：多语言通用语法解析（轻量结构扫描，V1 可选）
8. **pyright**：Python 类型校验（校验器，V1）与符号索引（后置可选）
9. **semgrep**：多语言静态缺陷扫描（后置可选）
10. **continue / aider**：Agent 调用代码底座的任务编排范式（仅架构参考）
11. **ccls**：大型工程索引、编译数据库处理思想（后置可选）

### D.2 沙盒族装配（与 DSH `examples/acp-agent/cordis.yml` 组合逐项一致）

落位 `lcode/planner/src/index.ts`（装配）+ `package.json`（peerDependencies）：

| DSH 组合（acp-agent） | L-CODE 落地 | ctx 服务 | 说明 |
|---|---|---|---|
| `dsh-sandbox-local` | `LocalSandboxProvider` | `ctx.sandbox` | 本地进程限制后端：Windows = ACL restricted-token runner（`sandbox-windows-acl`，enforcement=partial），Linux bwrap/Landlock、macOS Seatbelt；不可用即 fail-closed `SANDBOX_UNAVAILABLE`，绝不静默放行 |
| `dsh-sandbox-policy`（mode/workspaceRoot） | `SandboxPolicyService` | `ctx.sandboxPolicy` | 策略所有者：部署默认 mode + workspaceRoot + 每会话 `sandbox/mode` 事件覆盖（fold=last-wins）+ 向 systemPrompt 注入 `sandbox:policy` 上下文（DSH 逐字文案） |
| `dsh-user-approval`（policy=ask，danger→never） | `ApprovalService` | `ctx.approval` | 升级审批通道；无 answerer 时 ask fail-closed 为 `unavailable` |
| `dsh-fs-sandbox`（替换 `dsh-fs-local`） | `SandboxedFileSystem` | `ctx.fs` | 规划器侧 write/edit 每次调用按策略围栏：read-only 拒绝、workspace-write 限定 workspace+temp 根、danger 放行；read 放行；fs-observation-policy 正交叠加 |

- **部署默认**：`LCORE_SANDBOX_MODE`（read-only / workspace-write / danger-full-access），默认
  **workspace-write**（与 acp-agent 非快照默认一致；danger-full-access = V3.0 及之前行为 + 审批
  自动 never）。`workspaceRoot` 缺省 = planner cwd；agent 会话用会话 header 的 cwd。
- **每会话覆盖**：沿用 DSH `sandbox/mode` 事件（session-mode.ts 的 setSandboxMode/effectiveSandboxMode，
  随会话 JSONL 持久化、重放即状态）——桌面/未来 UI 切换即落一条事件。
- **运行时上下文**：`sandbox:policy` 贡献（order 110，DSH 逐字文案：read-only / workspace-write
  <root> / danger-full-access 三态），模型在每轮请求前看到当前文件效应策略。

### D.3 内核工具边界执行（策略随调用携带；拒绝文本与 DSH 逐字一致）

- 新增 `kernel/tools/sandbox_policy.py`（DSH 语义 Python 镜像）：
  - 模式：read-only / workspace-write / danger-full-access；
  - 写围栏（dsh-fs-sandbox `checkedTarget` 语义）：workspace-write 目标 canonical 后须在
    `writableRoots`（workspace_root + 平台 temp 根）内，越界抛 `SandboxDenied`；
  - 拒绝文本逐字 = `[sandbox: file access denied under <mode> mode]` +
    `[sandbox: escalation available — retry this exact operation once with sandbox_permissions
    (the narrowest wider mode that suffices) + justification; the approval prompt asks the user]`
    （tool-fs `mapError` 产出同款）。
- `kernel/api/main.py`：`PlannerToolRequest.sandbox`（{mode, workspace_root, session_id}）→
  `planner_tool` 围栏：read-only 拒绝 `MUTATION_TOOLS`（write_file/edit_file/shell/git_clone/
  build/run_check/flash，fail-closed：无 OS 级进程围栏时整工具拒绝）；workspace-write 对
  write_file/edit_file 的目标做根内校验；danger/缺省放行。响应 `{ok:false, sandbox_denied:true,
  sandbox_mode, error:<逐字文本>}`。
- `kernel/tools/chat_tools.py`：`ToolContext` 增 `sandbox` 字段（本次调用策略包，None=旧行为）。
- **规划器侧（`kernel-tools.ts`）**：每次调用 `ctx.sandboxPolicy.resolve({session})` 得
  {mode, workspace_root}；工具 schema 在策略装配时附加 `sandbox_permissions`/`justification`
  （枚举 workspace-write / danger-full-access，与 DSH tool-fs 同文案）；升级请求走
  `approveEscalation`（严格更宽 + `ctx.approval`，与 DSH `resolvePolicy` 同序），仅对本次调用
  生效；`kernel-client.tool()` 透传 sandbox 包。
- **规划器侧 fs 工具**（tool-fs）在 fs-sandbox 装配后自动带升级字段与围栏（tool-fs 自带
  `FsSandboxController`，无需自定义代码——"一模一样"的直接来源）。

### D.4 实测与边界

- 实测（本附录 V3.1）：
  - `kernel/tests/smoke_sandbox.py` **ALL_SANDBOX_TESTS_PASSED**：read-only 拒绝面 7 工具 +
    拒绝文本逐字比对；workspace-write 根内/子目录/大小写变体放行 + 外部拒绝；writableRoots 含
    平台 temp 根；danger/缺省/非法 mode 放行语义。
  - 规划器装配冒烟：沙盒族挂载顺序 trace（sandbox-local → sandbox-policy → user-approval →
    fs-sandbox → tool-fs）无异常，`/api/planner/health` 200（tool-fs 的 sandboxPolicy 不变量满足）。
- 已知边界（后续 Phase 完善）：
  - **内核子进程类工具无 OS 级进程限制**：shell/build/flash 等在 Python 内核侧执行，规划器
    ctx.sandbox（Windows ACL runner）管不到；read-only 下按整工具 fail-closed 拒绝（D.3），
    workspace-write 下由内核 cwd 防穿越约束——进程级隔离若需，另行在 Python 侧套 ACL/作业对象
    或把此类执行下沉规划器子进程（spike 评估）。
  - **升级审批 UI 后置**：`ctx.approval` ask 策略在无桌面 answerer 时 fail-closed（unavailable）；
    桌面审批弹窗按 Phase 5 工作台接线（同烧录确认先例）。当前部署默认 workspace-write/danger，
    常规编辑路径不触达升级。
  - `/api/planner/git_*`、烧录确认（flash_confirm/dismiss）为**显式用户操作**，不走沙盒策略
    （会话级确认已由桌面弹窗承载）；若需纳入，Phase 5 评审。
  - 事件字典新增 `sandbox/mode`、`approval/asked`、`approval/decided`（§5.2 表格未列，同
    flash/* 先例，Phase 5 统一回写）。

### D.5 验收口径与宿主工具面（V3.2 · 用户拍板）

> 排期表 V2.0（`docs/阶段3-DSH能力等价启用排期.md`）同步承载，本节为主文档侧记录。

**口径**：凡属 **agent 处理能力** 者与 DSH(rc.5) **一模一样**（同包装配 + 同语义）；UI/桌面等其它方面不追。

| 面 | 结论 |
|---|---|
| 必装（agent 处理能力 · DSH 默认基座一致） | 主循环全链路（含 request-error 重试钩子）、goal/skill/todo/guard、压缩、沙盒族（V3.1 ✅）、subagent（仅 in-process spawn/fork）、workflow、ralph、plan-mode（agent 侧）、fs 工具族标准集 |
| 可选（与 DSH 一致默认关） | **宿主工具族**（bash/pwsh/terminal/web/e2b/mcp 及 fs-search/str-replace）：rc.5 默认基座不含、按 overlay 启用；L-CODE 同此，启用时同名同 schema |
| 明确排除 | subagent 外部后端（acp/claude-code/codex，用户拍板只装 in-process）；UI/桌面/工作台渲染与桌面接线（Phase 5.4）；产品基建 D 类（telemetry/host-*/sqlite/session-query/feedback/schedule/identity/jobs/code-runtime/spill/context/agent-presets 等） |
| 产品扩展（不受影响） | 内核领域工具（build/flash/serial/git 会话安全/run_check 校验）——DSH 没有、按产品需求保留 |

**宿主工具族（E 类）落地原则**（可选 overlay，对应排期表 M-E）：
- **rc.5 事实**：默认基座不含模型可见宿主工具（仅 fs + bash 执行后端基建），web/pty/e2b 均按
  场景 overlay（web.cordis.yml / pty.cordis.yml / e2b.cordis.yml）启用——与 DSH 一致 = L-CODE
  同样默认不装、按需 overlay。
- 启用时注册 rc.5 **同名同 schema** 工具插件（`dsh-tool-bash`/`dsh-tool-pwsh`/
  `dsh-tool-terminal`/`dsh-tool-web`/e2b/`dsh-mcp-client`/fs-search/str-replace 等），模型可见
  面与 DSH 一字不差；bash/pwsh/terminal 走 ctx.sandbox（sandbox-local，V3.1 已备）。
- 后端可用性按"DSH 缺对应配置"行为处理：web-search 缺 provider key、e2b 缺云账号、mcp 缺外部
  server 时 = 不可用（与 DSH 一致），不为此改名或改变语义。
- 与内核 `shell`/领域工具**并存**：产品 persona 仍引导内核工具（build/flash/edit_file 等），
  并存期间以快照验收防行为分叉。
- Windows 风险 spike：bash.exe 可用性（git-bash）、pty、worker-thread（排期表 §8）。

**验收基线**：rc.5 `examples/acp-agent` 快照（tool-schemas / 系统提示词 / 拒绝与升级文本 /
会话 JSONL）逐条比对，覆盖：子 agent fan-out、workflow-run、ralph、plan、todo、越界写拒绝、
escalation 批准/拒绝、read-only 拒绝、宿主工具 schema。
